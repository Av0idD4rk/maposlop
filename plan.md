# План развития CTF-карты

## 1. Цель продукта

Сделать понятную и живую карту CTF, которая помогает школьникам и начинающим командам:

- находить подходящие соревнования рядом и онлайн;
- быстро понимать формат, ограничения, даты и правила участия;
- видеть активность CTF-сообщества не только в столицах, но и в малых городах;
- узнавать о командах своего города и их результатах;
- предлагать новые события, которые проходят модерацию перед публикацией.

Главная продуктовая метрика — число переходов к регистрации на CTF из малых и средних городов. Дополнительные метрики: доля регионов с актуальными событиями, число добавленных организаторами событий, конверсия карточка → регистрация, использование фильтров и доля импортов, прошедших модерацию без исправлений.

## 2. Что есть сейчас

MVP уже умеет:

- показывать интерактивную 3D-карту на детальных границах Natural Earth 1:10m;
- загружать опубликованные будущие CTF из Django API;
- автоматически геокодировать любой введённый в админке город и ставить флаг по его широте/долготе;
- группировать флаги по городам и раскрывать события при выборе региона;
- показывать описание, организатора, место и ссылку на регистрацию;
- открывать Яндекс Карты для отелей, маршрута и еды рядом с очным CTF;
- принимать предложения пользователей через публичную форму;
- модерировать предложения в стандартной Django Admin;
- учитывать `prefers-reduced-motion` и базовые мобильные размеры.

Текущий стек: Django 5.2.16, PostgreSQL в production (SQLite только локально), Redis,
SvelteKit (Svelte 5 + Three.js и D3-геопроекция внутри карты), TypeScript,
Vitest, Playwright и Vite. Код физически разделён на `backend/` и `frontend/`;
frontend-сборка попадает в `backend/static/dist/`. В репозитории настроены Ruff,
dependency audits и GitHub Actions для backend, frontend, production settings и
Chromium smoke-тестов.

## 4. Целевая модель данных

Сначала следует стабилизировать модель, иначе фильтры, импорт и статистика будут постоянно переделываться.

### География

- `Region`: официальный код, название, федеральный округ, `map_group_id`.
- `City`: название, административный регион, широта/долгота, источник координат и признак проверки. Экранные координаты не хранятся: они вычисляются общей проекцией карты.
- `Venue`: город, адрес, координаты, название площадки; опционально.
- Онлайн-событие не обязано иметь город. Очное событие обязано иметь проверенный город; гибридное — город очной части.

Геокодирование выполнять при импорте/редактировании, а не в браузере при каждом открытии. Администратор должен видеть точку на preview-карте и иметь возможность поправить её вручную.

### События

Расширить `Event`:

- `participation_mode`: online / onsite / hybrid;
- `game_format`: jeopardy / attack-defense / hack-quest / mixed / other;
- `stage`: independent / qualifier / semifinal / final;
- `audience`: open / school / student / academic / invited / individual;
- начало и конец регистрации отдельно от начала и конца игры;
- город/площадка, возрастные и командные ограничения;
- `source`, `source_url`, `external_id`, `last_synced_at`, `sync_status`;
- `participants_count`, `participants_updated_at` и явная подпись «по данным источника»;
- статус публикации: draft / needs_review / published / rejected / archived;
- `parent_event` для связи отборочного этапа с финалом.

Не смешивать два смысла слова «формат»: online/очность и Jeopardy/Attack-Defense должны быть разными полями и разными фильтрами.

### Региональные ограничения

- `EligibilityRule`: событие, тип include/exclude, регион, необязательное пояснение.
- Базовая политика события: `all_allowed`, `only_listed` или `all_except_listed`.
- Более общие ограничения (страна, возраст, школьники, студенты, приглашённые) хранить отдельно, а не кодировать в описании.
- В админке показывать итог до публикации: «допущено 12 регионов, исключено 3», проверять противоречия.

На карте при выборе события: город проведения выделять основным акцентом, допущенные регионы — вторичным цветом, исключённые — приглушать/штриховать. Всегда добавлять легенду и текстовый список, чтобы значение не передавалось одним цветом.

### Источники и дедупликация

- `ImportSource`: CTFtime, CTFNews/календарь, ручной ввод.
- `ExternalEvent`: source + external ID, checksum, raw JSON, timestamps, связь с `Event`.
- `ImportRun` и `ImportIssue`: состояние запуска, ошибки, число новых/обновлённых/конфликтных записей.
- Сначала дедупликация по `(source, external_id)`, затем кандидаты по нормализованному названию и пересечению дат; неоднозначные совпадения — только в очередь модерации.
- Внешнее обновление не должно молча затирать ручную правку: хранить provenance по полям или флаг `locked_by_editor`.

### Этап 2. Карточка события, умный фильтр и доступный каталог

1. Сделать полноценную карточку/URL события: описание, этап, два вида формата, даты игры и регистрации, место, ограничения, организатор, первоисточник, число команд и кнопки регистрации/поделиться.

4. Ранжировать результаты объяснимо: регистрация открыта → подходит пользователю → скоро начнётся → ближе географически. Показывать причину рекомендации, а не скрытый «умный» скоринг.
5. Сделать HTML-список равноправным карте: поиск и карточки должны работать без WebGL и с клавиатуры.
6. Покрыть фильтры unit-тестами и e2e-сценариями, включая пустые состояния.

Результат: пользователь за 2–3 действия находит CTF, в котором действительно может участвовать.

### Этап 3. Городские маркеры и огни флагов

1. Если указан проверенный город, ставить флаг в его точке; иначе явно использовать центр региона с подписью «точное место не указано».
2. При близком масштабе раскрывать события по городам, затем отдельные флаги; избегать наложений через cluster/spiderfy.
3. Ввести состояния огней: спокойный, скоро, регистрация закрывается, идёт сейчас. Интенсивность зависит от времени, а детализация — от масштаба карты.
4. Анимировать только `transform`/`opacity`, ограничивать частоту кадров, отключать свечение/волну при `prefers-reduced-motion` и на слабых устройствах.
5. Сделать статус различимым не только цветом: форма/иконка, подпись и легенда.
6. Провести тесты на реальных мобильных устройствах и проверить INP < 200 ms, отсутствие заметного CLS и приемлемый расход батареи.

Результат: приближение карты раскрывает реальные города, а огни помогают понять срочность, не превращаясь в визуальный шум.

### Этап 4. Агрегатор CTFtime и CTFNews

1. Начать с официального CTFtime API: импорт событий по временному окну, карточка по ID, организаторы, формат, onsite/location, restrictions, URL и `participants`.
2. Синхронизировать по расписанию с backoff, timeout, User-Agent, кешем и ограничением частоты; импортировать в draft/needs_review, а не сразу публиковать.
3. Соблюсти ограничение CTFtime: API предназначен для анализа и мобильных приложений и не разрешает делать клон сервиса. Использовать данные как один из источников карты, сохранять атрибуцию и ссылку на оригинал; при сомнении согласовать объём с CTFtime.
4. Число зарегистрированных команд показывать только если поле `participants` присутствует, вместе с временем обновления. Это snapshot источника, не гарантия фактического приезда.
5. Для CTFNews сначала согласовать допустимый канал. На сайте обнаружен публичный календарь, встроенный из Google Calendar, но отдельный документированный API не найден. Предпочесть официальный календарный feed/сотрудничество; HTML scraping включать только после проверки robots/условий и с низкой частотой.
6. Добавить ручную модерацию, предпросмотр diff, дедупликацию и алерты при систематических ошибках источника.
7. Не импортировать в карту новости, которые не являются соревнованиями; связь `NewsItem → Event` можно добавить отдельно.

Справочные точки на момент аудита:

- CTFtime API: <https://ctftime.org/api/>
- пример JSON события с `participants`: <https://ctftime.org/api/v1/events/165/>
- календарь CTFNews: <https://ctfnews.ru/calendar/>

Результат: новые соревнования регулярно попадают в очередь модерации, а не зависят только от ручного ввода.

### Этап 5. Поездка на очный CTF

1. Для onsite/hybrid-события с проверенным городом показать блок «Спланировать поездку».
2. Сформировать внешние ссылки: гостиницы на даты соревнования, маршрут до площадки, поиск еды/транспорта рядом. Начать с обычных URL/deep links Яндекс Карт/Путешествий, без сбора и перепродажи данных пользователя.
3. Не показывать блок для online-событий и событий без точного города.
4. Явно предупредить, что цены и наличие определяет внешний сервис; открывать ссылку только по действию пользователя.
5. Любую партнёрскую монетизацию помечать и проверять юридически отдельно.

Результат: карточка очного CTF помогает перейти от интереса к реальной поездке без разработки собственного сервиса бронирования.

### Этап 6. Команды, результаты и городские лидерборды

1. Создать `Team`, `TeamAlias`, `TeamHomeCity`, `EventResult`; внешние ID и источник обязательны для импортированных результатов.
2. Не считать одинаковые названия одной командой автоматически. Слияние алиасов — через уверенное правило или модератора, с журналом изменений.
3. Импортировать публичные результаты CTFtime после окончания событий; хранить место, баллы, дату snapshot и ссылку на источник.
4. Определить лидерборд города заранее: по домашнему городу команды, с отдельными срезами за год/всё время и прозрачной формулой. Место проведения CTF — фильтр статистики, а не автоматически «город команды».
5. Сделать две страницы: «команды из города» и «результаты соревнований, прошедших в городе», чтобы не смешивать разные смыслы.
6. Добавить механизм исправления принадлежности команды к городу и отметку неполных данных.

Результат: лидерборд можно объяснить и воспроизвести из источников, а команды малых городов получают видимость.

### Этап 7. Маршруты команд на карте

1. Строить маршрут только по публичным результатам очных событий с известным городом и хронологией.
2. Называть визуализацию «предполагаемый маршрут участия», потому что результат не доказывает физический перелёт или способ передвижения.
3. Онлайн-события исключать из географического маршрута или показывать отдельно без линии поездки.
4. Агрегировать на уровне команды; не отслеживать отдельных участников и не показывать текущую геопозицию.
5. По клику на сегмент показывать два события, даты и источники. Ограничить период/число линий, добавить фильтр команды и режим reduced motion.
6. Сначала выпустить статичную хронологию, затем анимированные дуги после проверки производительности и понятности.

Результат: карта показывает историю CTF-сообщества без ложного заявления о реальном трекинге людей.

## 6. Текущая и целевая архитектура

- Физическое разделение завершено: Django находится в `backend/`, Three.js/Vite — в `frontend/`; не возвращать исходники в корень.
- Django остаётся основным приложением и админкой.
- PostgreSQL обязателен в production; SQLite остаётся локальным вариантом разработки. Redis используется для общего rate limit и readiness.
- Периодические импорты сначала можно запускать management commands по cron/systemd timer. Очередь Celery/RQ добавлять только когда появятся долгие параллельные задачи и подтверждённая нагрузка.
- Внешние клиенты изолировать в `events/integrations/` с typed DTO, timeout, retry, rate limit и fixture-тестами.
- Публичное API v1 отдаёт только необходимые поля, имеет пагинацию; агрегаты и новые фильтры считать на сервере при росте данных.
- Frontend (SvelteKit, serverless SPA) разделён на API/state/data модули, доступный `EventCatalog`, dialogs и лениво загружаемый D3/Three.js `MapStage`. Полные продуктовые фильтры Этапа 2 остаются будущей задачей.
- Сырые ответы внешних сервисов не отдавать клиенту; хранить ограниченно для диагностики и дедупликации.
