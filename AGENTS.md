# AGENTS.md

## Назначение проекта

Это CTF-карта России: Django хранит и модерирует соревнования, SvelteKit-SPA (Three.js внутри компонента карты) отображает их на интерактивной карте. Продукт должен помогать школьникам и начинающим командам находить доступные CTF, особенно за пределами крупнейших городов.

Приоритеты при изменениях:

1. достоверность и происхождение данных;
2. безопасность публичной формы и админки;
3. доступность без мыши и без WebGL;
4. производительность на мобильных устройствах;
5. визуальные эффекты только после выполнения пунктов выше.

Актуальная продуктово-техническая дорожная карта находится в `plan.md`.

## Стек и структура

- `backend/ctfmap/` — настройки и URL Django-проекта.
- `backend/events/` — модели, admin, формы, API, миграции и management commands.
- `backend/events/views.index` — читает собранный `backend/static/dist/index.html` и отдаёт его как есть (с `@ensure_csrf_cookie`); серверного HTML-шаблона для главной страницы больше нет.
- `backend/manage.py`, `backend/requirements.txt` и `backend/requirements-dev.txt` — точка входа, runtime- и test/lint-зависимости.
- `frontend/src/routes/+page.svelte` — корневая страница, собирает компоненты из `frontend/src/lib/components/`.
- `frontend/src/lib/components/` — по компоненту на область UI: `Topbar`, `MapStage` (Three.js-рендер, поинтеры, зум, маркеры), `RegionPanel`, `EventCard`, `EventCatalog`, `Modal`, `EventModal`, `SuggestModal`, `ZoomControls`, `MapHint`.
- `frontend/src/lib/{api,catalog,event-data,stores,regions,format,travel,types}.ts` — HTTP-клиент, каталог, общие данные событий, состояние, composite-регионы, форматирование и travel-ссылки.
- `frontend/static/map/russia-regions.geojson` — подготовленные границы субъектов Natural Earth 1:10m; `scripts/build_map_data.py` воспроизводимо обновляет их и фильтрует только неразличимые микрополигоны.
- `frontend/svelte.config.js` — обёртка над `@sveltejs/adapter-static` в SPA-режиме (`fallback: 'index.html'`) с выводом в `backend/static/dist/`. Production-сборка размещает ассеты под `/static/dist`, после чего адаптер оставляет client router на `/` в bootstrap fallback-файла.
- `frontend/package-lock.json` — зафиксированные npm-зависимости.

Frontend — serverless SPA: SSR отключён (`export const ssr = false` в `+layout.ts`), собирается только статика, Node-сервер для фронтенда не нужен ни в dev, ни в проде. Не возвращать frontend/backend-исходники в корень репозитория. Не редактировать `backend/static/dist/`, `dist/`, `.svelte-kit/`, любые `node_modules/` и другие generated-файлы вручную. Менять исходники и пересобирать.

## Локальная настройка и проверки

PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r backend\requirements-dev.txt
Push-Location frontend
npm ci
npm run build
Pop-Location
Push-Location backend
python manage.py migrate
python manage.py runserver
Pop-Location
```

Минимальная проверка backend-изменения:

```powershell
Push-Location backend
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test
ruff check .
pip-audit -r requirements.txt
Pop-Location
```

Минимальная проверка frontend-изменения:

```powershell
Push-Location frontend
npm test
npm run check
npm run build
npm audit
npm run test:e2e
Pop-Location
```

`backend/static/.gitkeep` сохраняет корень статических файлов на чистом checkout,
поэтому самостоятельный `manage.py check` не должен выдавать `staticfiles.W004`.
Frontend build всё равно обязателен перед запуском пользовательской страницы.
Перед release выполнить dependency audits и `python manage.py check --deploy
--fail-level WARNING` с production settings. Не скрывать предупреждения увеличением
лимитов или отключением проверок без документированной причины.

## Правила данных и моделей

- Не объединять исходные административные коды регионов в БД. Москва/Московская область, Санкт-Петербург/Ленинградская область и Крым/Севастополь могут объединяться только на уровне визуальной `map_group`.
- Не хранить географически значимый город только свободным текстом. Событие с точным маркером должно ссылаться на нормализованный город/координаты и источник геоданных.
- Не смешивать формат игры (Jeopardy, Attack-Defense) с режимом участия (online, onsite, hybrid).
- Все импортированные сущности должны иметь `source`, внешний ID/URL и время обновления.
- Внешнее обновление не должно молча затирать ручное решение модератора.
- Не считать команды одинаковыми только по названию; использовать source ID, алиасы и очередь ручного разрешения конфликтов.
- Результат в очном CTF позволяет показать только предполагаемое участие в городе, но не доказывает физический перелёт или маршрут.
- При изменении модели создать миграцию, проверить существующие данные и добавить тест миграции, если преобразование нетривиально.

## Интеграции

- Предпочитать официальный API/feed сотрудничеству или HTML scraping.
- Перед подключением источника проверить его документацию, terms/robots и ограничения частоты.
- Для каждого HTTP-клиента задавать timeout, понятный User-Agent, ограниченный retry с backoff, rate limit и обработку частичного ответа.
- Не выполнять сетевые запросы к источникам при рендере пользовательской страницы. Импортировать по расписанию и отдавать данные из локальной БД.
- Геокодирование нового города выполняется только при явном сохранении в админке, не чаще одного запроса в секунду, с timeout/User-Agent и сохранением результата в `City`; URL провайдера должен настраиваться через окружение.
- Новые/конфликтные события из агрегатора сначала помещать в `draft`/`needs_review`.
- CTFtime использовать с атрибуцией и ссылкой на оригинал; не превращать проект в клон CTFtime.
- CTFNews не парсить агрессивно. До появления документированного API использовать согласованный календарный feed или ручную модерацию.
- Тесты интеграций должны использовать сохранённые fixtures/mocks, а не реальную сеть.

## Backend

- Представления должны проверять метод, content type, размер тела, JSON и ошибки валидации; публичные POST endpoints должны иметь CSRF и anti-abuse защиту.
- Не отдавать contact email, admin notes, сырые payload или внутренние статусы через публичное API.
- Для bulk admin actions использовать `transaction.atomic()` и не отмечать исходную запись обработанной, если создание целевой записи не удалось.
- Даты хранить timezone-aware в UTC, отображать с явно выбранным часовым поясом.
- Для растущих списков добавлять пагинацию, фильтры и индексы; не сериализовать неограниченную историю целиком.
- Production secrets, hosts, cookies и DB URL читать из окружения. Никогда не коммитить реальные ключи, токены или `.env`.
- Логи не должны содержать секреты, полное тело пользовательской формы, email или другие персональные данные без необходимости.
- Стабильный публичный контракт находится под `/api/v1/`; legacy `/api/` поддерживать только как явно документированный переходный alias.
- `/health/` проверяет процесс, `/ready/` — БД и общий cache; readiness не должна маскировать недоступную зависимость.
- Rate limit публичной формы должен использовать общий Redis cache в production и завершаться безопасной ошибкой при недоступности cache.

## Frontend, карта и дизайн

- Карта не может быть единственным способом найти событие. Поддерживать доступный HTML-список/поиск и понятное состояние при отсутствии WebGL.
- Three.js-карту загружать лениво после критического HTML; сбой карты не должен ломать каталог и карточки событий.
- Интерактивные элементы должны работать с клавиатурой, иметь видимый `:focus-visible`, корректное имя и цель не меньше 44×44 px.
- Не передавать формат, допуск или срочность только цветом; добавлять текст/иконку/легенду.
- Соблюдать `prefers-reduced-motion`. Анимировать преимущественно `transform` и `opacity`; не запускать тяжёлые эффекты на слабых/мобильных устройствах.
- Огни флагов отражают полезное состояние (скоро старт, закрывается регистрация, идёт сейчас), а не являются постоянным декоративным шумом.
- Если город не проверен, использовать центр региона и явно сообщать о приблизительности маркера.
- Любой текст из API считать недоверенным. Предпочитать `textContent`; при формировании HTML экранировать все значения и не допускать небезопасных URL.
- Проверять desktop, viewport около 760 px и небольшой mobile viewport. Следить за INP, CLS, размером bundle и числом одновременно отрисовываемых маркеров.
- Не добавлять новую animation/3D-библиотеку, если задачу уже решает Three.js/CSS и выигрыш не подтверждён.

## Тестирование

Для исправления бага сначала добавить или описать воспроизводящий тест. Покрывать по уровню риска:

- модели и API — Django tests;
- фильтры, проекцию и форматирование — unit tests TypeScript;
- главные сценарии — Playwright: загрузка, фильтр, открытие карточки, предложение события, клавиатура, mobile и reduced motion;
- импорт — fixture-тесты новых/обновлённых/дублирующихся/битых ответов;
- admin actions — success, validation failure, повторный запуск и транзакционность.

Не считать изменение готовым только потому, что компилятор проходит. Для UI нужен хотя бы smoke-тест в браузере, для миграции — запуск на копии реалистичных данных.

## Безопасность и приватность

- Любой показанный пользователем секрет считать скомпрометированным и рекомендовать немедленную ротацию; не использовать и не записывать его в файлы/логи.
- Не ослаблять CSRF, XSS-защиту или CORS ради быстрого обхода проблемы.
- Для публичных предложений применять rate limit, honeypot/CAPTCHA по риску и политику удаления контактных данных.
- Не отслеживать перемещения отдельных участников. Маршруты команд строить только из публичных результатов очных соревнований и подписывать как предполагаемые.
- Внешние ссылки открывать по явному действию пользователя с `rel="noopener noreferrer"`; партнёрские ссылки помечать.

## Git и документация

- Сохранять пользовательские незакоммиченные изменения и не выполнять destructive git-команды без прямого запроса.
- Коммиты делать небольшими и тематическими: модель/миграция, API, UI и тесты по возможности разделять.
- Не редактировать старые миграции после их применения; создавать новую.
- При изменении команд, переменных окружения, API или архитектуры обновлять README и этот файл.
- Если реализация меняет приоритеты или допущения дорожной карты, обновить `plan.md` вместе с кодом.

## Definition of Done

Изменение готово, когда:

- выполнены критерии задачи и обработаны loading/empty/error состояния;
- добавлены тесты, соответствующие риску;
- frontend `npm run build`, затем backend `python manage.py check`, миграционные проверки и тесты проходят из своих рабочих каталогов;
- проверены keyboard/mobile/reduced-motion сценарии для UI;
- новые внешние данные имеют provenance и fallback;
- production-конфигурация проходит `check --deploy --fail-level WARNING`, а health/readiness имеют smoke-тесты;
- в diff нет секретов, персональных данных, случайных generated-файлов и unrelated-изменений;
- документация обновлена.
